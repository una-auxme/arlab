# 2. Architecture Constraints
<!-- Anything that constrains the team in design and implementation decisions or decision about related processes. Can sometimes go beyond individual systems and are valid for whole organizations and companies. -->

This section outlines the key constraints that limit design and implementation decisions, including technical, organizational, and political factors.

## Technical Constraints

| Constraint Category    | Constraints |
----------------------|
| Hardware Compatibility | - must run on Jetson Nano<br>- must support the selected robot arm and gripper<br>- must support the robot platform including omni-wheels<br>- must support multiple sensors (RGB-D cameras, LIDAR) with reliable data acquisition |
| Real-time Capability   | - motion control, grasping, object detection must operate as close to real-time as possible<br>- safety-critical data must be processed in real-time<br>- system reaction time for HRI must be acceptable |
| Power Management       | - must operate within available battery capacity<br>- system must handle safe shutdown if battery is low |
| Network / Communication| - communication between nodes for distributed computation must be reliable and low-latency |
| Modularity             | - components must be modular to allow easy upgrades or replacement without affecting overall system functionality |

---

## Organizational Constraints

| Constraint Category   | Constraints                                                                                                                                                         |
|-----------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Languages/ Code       | - python & C++<br>- code commentation with google style                                                                                                             |
| Experience / Resources| - limited experience with ROS2<br>- limited development time → preferred use of existing software components<br>- simulator limitations reduce testing possibilities|
| Team Knowledge        | - team members already familiar with behavior trees, motion planning, and SLAM                                                                                      |
| License               | - contents included in the project should be Open Source published under the MIT license                                                                            |
| Time-frame            | - limited development time caused of the semester/course duration                                                                                                   |

---

## Conventions

| Constraint Category    | Constraints                                                                                          |
|------------------------|------------------------------------------------------------------------------------------------------|
| Knowledge Base         | - use of SQLAlchemy                                                                                  |
| Navigation / Movement  | - use of Nav2 & SLAM for navigation and mapping                                                      |
| Manipulation           | - use of MoveIt2 for motion planning                                                                 |
| Computer Vision        | - use of YOLO CNN for object detection                                                               |
| Perception             | - use of pyrealsense2 for camera integration<br>- use of rplidar_ros2 for lidar integration          |
| Documentation          | - use of arc42 templates<br>- document each of the modules and services/functions in the code itself |
| Linting                | - ruff linter and code formatter                                                                     |

## Safety Constraints (Specific)

| Constraint Category   | Constraints                                                                    |
|-----------------------|--------------------------------------------------------------------------------|
| Redundancy            | - safety must be ensured even if individual components fail                    |
| Safe Human Interaction| - system must always operate safely around humans                              |
| Emergency Handling    | - system must respond to sensor failures or unexpected obstacles appropriately |
