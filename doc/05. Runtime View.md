The runtime scenarios are shown in a numbered list of steps that are processed in sequential order.

## Runtime Scenario 1 — Object Manipulation (from command to grasp)

### Steps 1

1. Decision Making starts a ManipulationAction on the Orchestrator. The action includes the ManipulationCommand containing what to do and the ID of the object to manipulate.
2. Orchestrator queries the Knowledge Base for object metadata (name, bounding box, point cloud).
3. Orchestrator calls the Gripping Parameter Service with object properties to obtain the required gripping force, grasp type and grasp constraints.
4. Orchestrator transforms the object’s point cloud and bounding box into the Manipulator Base coordinate frame.
5. Orchestrator derives a target pose: position from the point cloud; orientation from the bounding box.
6. Orchestrator pulls the scene geometry from the database.
7. Orchestrator publishes the target pose, scene geometry, and constraints to MoveIt (planning scene & goal).
8. MoveIt plans a collision-free trajectory and returns the planned path (or a failure status).
9. Job-Runner commands the manipulator to execute the trajectory.
10. End-effector closes according to the objects defined grip type and applies the computed gripping force to grasp the object.
11. Job-Runner activates the hand force sensors stream
12. Job-Runner activates the hand force monitor to detected if an object is dropped while placing.
13. Orchestrator reports success/failure back to Decision Making and logs the outcome as a RobotStatusEvent in the Knowledge Base.

### Error handling 1

The ManipulationAction can be cancelled by the manipulation Orchestrator (or Decision Making) at any time. In this case an ActionResponse is still returned providing feedback to Decision Making allowing it to properly handle the error.

## Runtime Scenario 2 — Database: Create/Update Entity

### Steps 2

1. Requesting Node calls the appropriate “Create/Update Entity” service.
2. Service converts ROS message → database schema format.
3. Service stores or updates the entity record in the database.
4. Database returns an operation result (success/failure + id of the new/updated Entity).
5. Service returns the id of the new/updated Entity or an error (message + type)

---

## Runtime Scenario 3 — Database: Get Entity

### Steps 3

0. Optional: Node gets a list of all existing Entity-IDs in the database with the "GetEntities" service
1. Requesting Node calls the "GetEntity" service with the ID.
2. Database retrieves the entity with the specified ID.
3. Database returns both result status and the Entity data.
4. Service converts database schema data/result → ROS message.
5. Requesting Node verifies the result and consumes the returned data.

## Runtime Scenario 4 — Movement Orchestration (start/stop navigation processes)

### General steps 4

1. A client (e.g. Global Decision Making) sends a MovementAction goal on `/movement/action` with `cmd` and `enable`.
2. The Orchestrator accepts every goal and validates the command during execution.
3. Depending on `cmd`, the Orchestrator:
   - `localization` / `mapping` / `nav`: starts or stops AMCL, SLAM Toolbox or Nav2 as a separate process. A process that is already running is not started twice.
   - `auto_annotate`: starts or stops the auto-annotation (see [Runtime Scenario 9](#runtime-scenario-9--mapping-drive-with-auto-annotation)).
   - `map_save`: saves the latest map to file and, if enabled, to the Knowledge Base via `AddMap`.
   - `stop_all`: stops auto-annotation and all navigation processes.
4. During execution the Orchestrator publishes `status` feedback.
5. The Orchestrator returns the result with `error_code`, `message` and `success`.

### Error handling 4

The goal always succeeds; the outcome is carried in the result, which clients must inspect via `success` and `error_code`:
`BAD_COMMAND` (unknown `cmd`), `PROCESS_START_FAILED` (process exits within 2 s after start), `PROCESS_STOP_FAILED`, `MAP_SAVE_FAILED`, `DB_SERVICE_UNAVAILABLE`, `DB_SAVE_FAILED` or `ANNOTATE_SERVER_UNAVAILABLE`.
If a goal is cancelled, the Orchestrator stops auto-annotation and all navigation processes.

## Runtime Scenario 5 — Safety Monitoring (flawless vs. local issue)

### Flawless scenario 5

1. Safety submodules register with the central Safety Node.
2. Submodules continuously publish periodic status updates (heartbeats/health).
3. Central Safety Node aggregates statuses, detects no anomalies. When all is in order, no intervention is necessary.
4. Normal operation continues.

### Local fatal issue scenario 5

1. Safety submodules register with the central Safety Node.
2. Submodules continuously publish periodic status updates.
3. A submodule detects a fatal issue and reports it to the central Safety Node.
4. The Central Safety Node evaluates severity, context, and required handling.
5. The Central Safety Node sends out a RobotStatusEvent and initiates a system-wide freeze.
6. Decision Maker receives the RobotStatusEvent and cancels all running actions. It now waits for the next safety status event.
7. The Central Safety Node makes the Robot transition to a safe state. (e.g. blocking motor movement)
8. The Central Safety Node starts mitigation strategies (e.g. restarting nodes)
9. The Central Safety Node waits until a safe state has been reached (e.g. human left the vicinity, nodes have been restarted)
10. Central Safety Node sends out a RobotStatusEvent containing normal safety status
11. The Decision Maker resumes normal operation

### Local nonfatal issue scenario 5

1. Safety submodules register with the central Safety Node.
2. Submodules continuously publish periodic status updates.
3. A submodule detects a nonfatal issue and does not report it to the central Safety Node. It is only handled locally.
4. E.G. Speed to high
5. The local speed safety node forces the speed to 0.0 and triggers new planning on the movement orchestrator.

## Runtime Scenario 6: Vision Snapshot into the Knowledge Base

### Steps 6

1. A client sends a goal on the `/vision/snapshot` action. Object detection processes a frame only on request. The goal's `VisionSnapshotCommand` sets `clear_database`, `mask_hand` (blanks the lower 20% of each mask to suppress the robot's own gripper) and any `extra_models` to run.
2. Object detection drops its cached frame and waits up to 5 s for a fresh RGB + point cloud pair, since the arm-mounted camera may still hold a frame from before the robot moved.
3. The point cloud is transformed into `target_frame` (`world` in the integrated launch) and projected into the color image, so its points can be tested against the segmentation masks.
4. All pinned models plus the requested `extra_models` run on the frame. Non-pinned models are loaded on demand and released again after an idle timeout.
5. Per detection, the point cloud is filtered by that detection's mask and reduced to its largest DBSCAN cluster.
6. Object detection builds one Entity + Shape pair per detection: the class label maps to an entity type via the label configuration, the pose is the centroid of the points, the filtered cloud becomes the shape.
7. Each pair is stored with two service calls: "AddEntity" returns the new entity ID, "UpdShape" then attaches the geometry to it.
8. If `clear_database` was requested, the pickables that were stored before this snapshot are deleted. Only pickables are removed, so furniture and humans survive.

Entities are neither merged nor deduplicated: each snapshot replaces the pickables wholesale, so the same object detected twice receives a new ID each time.

### Error handling 6

The goal always succeeds; the outcome is carried in `VisionSnapshotResponse.result`, which clients must inspect: `SUCCESS`, `ERROR_NO_IMAGE_DATA` (no frame within the 5 s window, nothing written) or `ERROR_UNKNOWN` (processing raised, detail in `error_msg`).
Knowledge Base failures and models that cannot be loaded are logged and skipped rather than failing the goal.

## Runtime Scenario 7 - HRI + Vizbox: Robot requests the operator to open the cabinet door

1. Robot navigates to cabinet
2. Perception detects a closed cabinet door -> in database
3. Decision maker checks the is_open state of the cabinet -> it is closed
4. Decision maker sends a help request to the HRI with the message "Please open the cabinet door"
5. The HRI tells the LLM to rephrase the help request for the user
6. The LLM output is
   - converted into audio and output via the speakers
   - sent to the vizbox
   - is then part of the llm chat history
7. The Decision maker waits until the cabinet is detected open (checks the database every tick)
8. The Decision maker sends a feedback message to the HRI "Thank you" -> LLM -> Audio

If the waiting in 7. times out, the Decision maker retries from 4.

## Runtime Scenario 8 - HRI + Vizbox: The operator requests something from the robot

Note that this scenario is currently not a necessity since the tasks we aim for do not require it.

1. Operator talks to the robot
2. The VoiceActivityDetection node detects voice activity
3. The SpeechToText node starts converting audio into text
4. The text is fed into the llm with the request to check if it is relevant to the previous conversation or to the robot in general
5. If no the VoiceActivityDetection waits until it stops detecting voice for a certain amount of time and the cycle restarts from 1.
6. If yes the text is input
   - to the llm as a new user input
   - to the vizbox
   - is then part of the llm chat history
7. The LLM output is
   - converted into audio and output via the speakers
   - sent to the vizbox
   - is then part of the llm chat history
8. If the LLM also requests a tool call, the tool call is validated and sent to the Decision maker

The whole chat history is kept inside the LLM chat node and the oldest messages are discarded if the context gets too long

## Runtime Scenario 9 — Mapping Drive with Auto-Annotation

### Steps 9

1. The operator starts `mapping_drive.launch.py`, which starts the Knowledge Base, Object Detection (with `target_frame` = `map`) and the Orchestrator.
2. After `mapping_delay` (default 2 s) the launch file sends the `mapping` goal, the Orchestrator starts SLAM Toolbox.
3. After a further `slam_settle_time` (default 8 s), so the `map` frame is available, the launch file sends the `auto_annotate` goal.
4. The Orchestrator waits for the `/vision/snapshot` action server, subscribes to odometry and starts a timer.
5. The operator drives the robot through the environment.
6. On each tick (default 1 s) the Orchestrator checks the snapshot conditions:
   - no snapshot is currently running
   - the robot is moving slowly (linear speed < 0.10 m/s, turn rate < 0.20 rad/s)
   - at least 6 s have passed since the last snapshot
   - the robot has moved ≥ 0.75 m or turned ≥ 0.5 rad since the last snapshot
7. If all conditions are met, the Orchestrator publishes `true` on `/arlab/movement/annotating` so the operator holds position, and sends a snapshot goal with `clear_database` = `false`.
8. Object Detection runs the snapshot (see [Runtime Scenario 6](#runtime-scenario-6-vision-snapshot-into-the-knowledge-base)) and writes the detected entities into the Knowledge Base in the `map` frame.
9. When the snapshot is done, the Orchestrator publishes `false` on `/arlab/movement/annotating` and the checks continue with the next tick.

The thresholds are parameters in `arlab_navigation_params.yaml`.

### Error handling 9

- If the snapshot action server is not available within 10 s, the `auto_annotate` goal returns `ANNOTATE_SERVER_UNAVAILABLE`.
- If SLAM Toolbox is not running when auto-annotation starts, the Orchestrator logs a warning, since the `map` frame may be unavailable.
- A rejected or failed snapshot is logged, and the next snapshot is attempted on a later tick.
- Auto-annotation is stopped by `auto_annotate` with `enable` = `false`, by `stop_all` or by cancelling the goal.

## Runtime Scenario 10 — Manual Entity Placement

### Steps 10

1. The operator sets the topic of the RViz "2D Goal Pose" tool to `/arlab/entity_pose` and clicks a pose on the map.
2. The Entity Placer transforms the pose into the target frame (default `map`) and stages it. A new click replaces the staged pose.
3. The operator calls `/arlab/entity_placer/place` with the entity data (AddEntity request).
4. The Entity Placer sets pose, `pose_reference_frame` and `stamp` from the staged pose and calls `AddEntity` on the Knowledge Base.
5. The Entity Placer returns the new entity ID and the result. The entity is shown in RViz on `/arlab/knowledge/visualization`.

### Error handling 10

- If the pose cannot be transformed into the target frame, the error is logged and the pose is not staged. A previously staged pose remains.
- If no pose is staged, the service returns `ERROR_INVALID_INPUT`.
- If `AddEntity` is not available within 5 s, the service returns `ERROR_BUSY`. If the call fails, it returns `ERROR_DBAPI`.
- The staged pose is kept after placing, so calling the service again adds another entity with the same pose.
