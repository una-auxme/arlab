### Movement

1. Orchestrator receives High-Level movement command from Global Desicion Making (containing: activate_mapping(bool), activate_localization(bool), destination(DestinationType))
2. Orchestrator differentiates between whether it should activate mapping, activate localization and/or setting a Destination
3. Depending on the Task, the according Nav-Stack Node is being notified and started/shutdown (Nav2, Localization, SLAM)

#### Example: Robot should travel to destination with both, mapping and localization activated

1. High level movement command with activate_mapping=true, activate_localization=true and a destination (assuming map has already been suitably pregenerated)
2. Orchestrator separates the arguments. The destination gets evaluated on whether the destination is already known (lookup in knowledge base), is a direct input (coordinate) or whether the destination is following a person (activate leg tracking)
3. The localization will be activated because activate_localization=true
4. SLAM node will be started (activate_mapping=true)
5. According to the type of destination mentioned in point 2, the navigation node will output messages on the cmd_vel topic to provide velocity/direction commands to the simulation/hardware

## Runtime Scenario 1 — Object Manipulation (from command to grasp)

**Textual description (steps):**
1. Decision Making starts a manipulation action on the Orchestrator, including the object ID.
2. Orchestrator queries the Knowledge Base for object metadata (name, bounding box, point cloud).
3. Orchestrator calls the Gripping Force Service with object properties to obtain the required gripping force and grasp constraints.
4. Orchestrator transforms the object’s point cloud and bounding box into the Manipulator Base coordinate frame.
5. Orchestrator derives a target pose: position from the point cloud; orientation from the bounding box.
6. Orchestrator publishes the target pose, scene geometry, and constraints to MoveIt (planning scene & goal).
7. MoveIt plans a collision-free trajectory and returns the planned path (or a failure status).
8. Orchestrator commands the manipulator to execute the trajectory.
9. End-effector applies the computed gripping force to grasp the object.
10. Orchestrator reports success/failure back to Decision Making and logs the outcome in the Knowledge Base.

**Notable interaction aspects:**
1. Clear separation of concerns: Knowledge Base (perception data), Orchestrator (coordination), MoveIt (planning), Gripping Force Service (actuation constraint).
2. Consistent frame transforms are critical before pose estimation and planning.
3. Safety/limits: the gripping force and orientation constraints bound MoveIt’s feasible solutions.
4. Result logging enables later optimization and error analysis.

## Runtime Scenario 2 — Database: Create/Update Entity

**Steps:**
1. Requesting Node calls the appropriate “Create/Update Entity” service.
2. Service converts ROS message → database schema format.
3. Service stores or updates the entity record in the database.
4. Database returns an operation result (success/failure + metadata).
5. Service converts database schema result → ROS message.
6. Requesting Node validates the received result and proceeds accordingly.

---

## Runtime Scenario 3 — Database: Load Entity

**Steps:**
1. Requesting Node calls the “Load Entity” service with selection criteria.
2. Service converts ROS message → database query/schema format.
3. Database retrieves the entity/data.
4. Database returns both result status and the data payload.
5. Service converts database schema data/result → ROS message.
6. Requesting Node verifies the result and consumes the returned data.

## Runtime Scenario 4 — Movement Orchestration (activate mapping/localization/destination)

**General steps:**
1. Global Decision Making sends a high-level movement command to the Orchestrator: `activate_mapping (bool)`, `activate_localization (bool)`, and `destination (DestinationType)`.
2. Orchestrator parses the command and decides which Nav-Stack components to bring up/shut down (Nav2, Localization, SLAM).
3. Orchestrator evaluates the destination type:
   - Known place → lookup in Knowledge Base.
   - Direct coordinate → validate and transform as needed.
   - Follow person → enable leg tracking.
4. Orchestrator starts/stops Localization and/or SLAM according to flags.
5. Navigation node computes path and publishes `cmd_vel` to simulation/hardware.
6. Orchestrator monitors progress and reports completion or errors back to Decision Making.

**Example — “Go to destination with mapping & localization active” (map pre-generated):**
1. Orchestrator receives: `activate_mapping=true`, `activate_localization=true`, plus destination.
2. Orchestrator identifies destination type (KB lookup / coordinate / follow target).
3. Localization is started (flag true).
4. SLAM node is started (flag true).
5. Navigation node plans and publishes `cmd_vel` until the robot reaches the destination; Orchestrator reports status.

## Runtime Scenario 5 — Safety Monitoring (flawless vs. local issue)

**Flawless scenario:**
1. Safety submodules register with the central Safety Node.
2. Submodules continuously publish periodic status updates (heartbeats/health).
3. Central Safety Node aggregates statuses, detects no anomalies, and forwards “all-green” state to the system.
4. Normal operation continues.

**Local issue scenario:**
1. Safety submodules register with the central Safety Node.
2. Submodules continuously publish periodic status updates.
3. A submodule detects an issue and reports it to the central Safety Node.
4. Central Safety Node evaluates severity, context, and required handling.
5. Central Safety Node executes a predefined mitigation strategy (e.g., slow down, stop arm, replan) or initiates a system-wide freeze.
6. Orchestrator and affected modules receive the mitigation command and transition to the safe state; incident is logged.
