### Movement

1. Orchestrator receives High-Level movement command from Global Desicion Making (containing: activate_mapping(bool), activate_localization(bool), destination(DestinationType))
2. Orchestrator differentiates between whether it should activate mapping, activate localization and/or setting a Destination
3. Depending on the Task, the according Nav-Stack Node is being notified and started/shutdown (Nav2, Localization, SLAM)

#### Example: Robot should travel to destination with both, mapping and localization activated

1. High level movement command with activate_mapping=true, activate_localization=true and a destination (assuming map has already been suitably pregenerated)
2. Orchestrator separates the arguments. The destination gets evaluated on whether the destination is already known (lookup in knowledge base), is a direct input (coordinate) or whether the destination is following a person (activate leg tracking)
3. The localization will be activated because activate_localization=true
4. SLAM node will be started (activate_mapping=true)
5. According to the type of destination mentioned in point 2, the navigation node will output messages on the cmd_vel topic to provide velocity/direction commands to the simulation/hardware

#### Case

Safety
Runtime view – flawless scenario

1. Safety submodules register with the central safety node.
2. Submodules continuously send periodic status updates to the central safety node.

Runtime view – local issue scenario

1. Safety submodules register with the central safety node.
2. Submodules continuously send periodic status updates to the central safety node.
3. An issue occurs in a submodule.
4. The submodule local safety node reports the issue to the central safety node.
5. The central safety node evaluates the issue and determines the required handling.
6. The central safety node either executes a predefined mitigation strategy or initiates a system-wide freeze.
