# 9. Architecture Decisions

This section describes specific architectural decisions that are considered important, expensive, critical, risky or large scale.

## Manipulation

| **Decision**                 | **Description**                                    | **Reason**                                                                                                   |
|------------------------------|----------------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| MoveIt2                      | Usage of MoveIt2 as the manipulation platform      | well-established and reliable library; broad hardware support                                                |
| local-gripping-force service | Usage of a local-gripping-force estimation-service | gripping force estimation is only needed within the manipulator                                              |
| Predefined Commands          | Usage of predefined driving commands               | simplifies the decision making, since the orchestrator can only choose 1 out of a predefined set of commands |

---

## Movement

| **Decision**           | **Description**                                                                                                                | **Reason**                                                                                                                                     |
|------------------------|--------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| Orchestrator           | Implementation of an orchestrator as an translation layer between makro task from decision making and specific micro tasks     | Modularization; common source of information/commands for all movement related nodes                                                           |
| Nav2                   | Usage of Nav2 as the navigation platform                                                                                       | Professionally supported ROS2 successor of the navigation stack; proven and reliable;                                                          |
| SLAM                   | Usage of SLAM for mapping                                                                                                      | Reliable and proven; open source slam-toolbox                                                                                                  |
| Leg Tracking Processor | Implementation of a leg tracking processor to distinguish persons from objects and to enable the robot to follow humans around | Safety distance between robot and human should be bigger than between robot and objects; RoboCup rulebook requires the robot to follow persons |

---

## Decision Maker

| **Decision**               | **Description**                                                                                                           | **Reason**                                                                                       |
|------------------------|-----------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------|
| Controls Orchestrators | Controls the orchestrator of both manipulation and movement by starting their actions; only controls global task flow | separates the "what should be done" from the "how it should be done"; enables modularization |

---

## Database

| **Decision**        | **Description**                                      | **Reason**                                                                                                                        |
|---------------------|------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------|
| Relational Database | Chosing relational database over ontology            | relational databases are well-known and proven & little to no semantics are required; team has no prior experience with onologies |
| SQLAlchemy          | Using SQLAlchemy to operate the database with python | Easy to use, popular and proven python library; supports async; has ORM suport for python classes                                 |

---

## Safety

| **Decision**                | **Description**                                                                                                                                                                                                                                                                                     | **Reason**                                                                                                                                                                                                                  |
|-----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Safety templates            | Each module of the robot implements its safety locally, using templates; safety integration directly into the development process without extra overhead                                                                                                                                            | No dedicated safety team affordable & external enforcement would slow down development                                                                                                                                      |
| Local safety submodules     | Local safety submodules with simple templates keep safety close to the local functionality and local parameters, allowing for quick intervention and adjustment                                                                                                                                     | A centralized safety logic would become complex and hard to adapt as features evolve                                                                                                                                        |
| Central safety control node | A central safety control node collects all submodule states and evaluates severity; ensures uniform reactions across the system                                                                                                                                                                     | Without structured aggregation, local errors remain hidden and handling becomes inconsistent; creates a single source of truth for audits and certification                                                                 |
| Data Pipeline               | Creation of a data pipeline that includes perception, computer vision modules, processing and interpreting visual data from multiple sensors. Using this pipeline enables scalability with sensors, specific processing at multiple stages, simple implementation and a clean separation of context | All system components have varying sensor data needs at different times. This approach ensures that each component can access the specific data it requires when its needed, reducing redundancy and optimizing performance |
