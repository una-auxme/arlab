### Movement

1. Orchestrator receives High-Level movement command from Global Desicion Making (containing: activate_mapping(bool), activate_localization(bool), destination(DestinationType))
2. Orchestrator differentiates between whether it should activate mapping, activate localization and/or setting a Destination
3. Depending on the Task, the according Nav-Stack Node is being notified and started/shutdown (Nav2, Localization, SLAM)

#### Example: Robot should travel to destination with both, mapping and localization activated

1. High level movement command with activate_mapping=true, activate_localization=true and a destination (assuming map has already been suitably pregenerated)
2. Orchestrator separates the arguments. The destination gets evaluated on whether the destination is already known (lookup in knowledge base), is a direct input (coordinate) or whether the destination is following a person (activate leg tracking)
3. The localization will be activated because activate_localization=true
4. SLAM node will be started (activate_mapping=true)
5. According to the type of destination mentioned in point 2, the navigation node will output messages on the cmd_vel topic to provide velocity/direction commands to the simulation/hardware

## Runtime Scenario 1 — Object Manipulation (from command to grasp)

### Steps 1

1. Decision Making starts a ManipulationAction on the Orchestrator. The action includes the ManipulationCommand containing what to do and the ID of the object to manipulate.
2. Orchestrator queries the Knowledge Base for object metadata (name, bounding box, point cloud).
3. Orchestrator calls the Gripping Force Service with object properties to obtain the required gripping force and grasp constraints.
4. Orchestrator transforms the object’s point cloud and bounding box into the Manipulator Base coordinate frame.
5. Orchestrator derives a target pose: position from the point cloud; orientation from the bounding box.
6. Orchestrator pulls the scene geometry from the database.
7. Orchestrator publishes the target pose, scene geometry, and constraints to MoveIt (planning scene & goal).
8. MoveIt plans a collision-free trajectory and returns the planned path (or a failure status).
9. Orchestrator commands the manipulator to execute the trajectory.
10. End-effector applies the computed gripping force to grasp the object.
11. Orchestrator reports success/failure back to Decision Making and logs the outcome as a RobotStatusEvent in the Knowledge Base.

### Error handling 1

The ManipulationAction can be cancelled by the manipulation Orchestrator (or Decision Making) at any time. In this case an ActionResponse is still returned providing feedback to Decision Making allowing it to properly handle the error.

## Runtime Scenario 2 — Database: Create/Update Entity

### Steps 2

1. Requesting Node calls the appropriate “Create/Update Entity” service.
2. Service converts ROS message → database schema format.
3. Service stores or updates the entity record in the database.
4. Database returns an operation result (success/failure + id of the new/updated Entity).
5. Service returns the id of the new/updated Entity or an error (message + type)

## Runtime Scenario 3 — Database: Get Entity

### Steps 3

0. Optional: Node gets a list of all existing Entitiy-IDs in the database with the "GetEntities" service
1. Requesting Node calls the "GetEntity" service with the ID.
2. Database retrieves the entity with the specified ID.
3. Database returns both result status and the Entity data.
4. Service converts database schema data/result → ROS message.
5. Requesting Node verifies the result and consumes the returned data.

## Runtime Scenario 4 — Movement Orchestration (activate mapping/localization/destination)

### General steps 4

1. Global Decision Making starts a MovementAction on the Orchestrator. It includes the MovementCommand.
2. Orchestrator parses the command and decides which Nav-Stack components to bring up/shut down (Nav2, Localization, SLAM).
3. Orchestrator evaluates the destination:
   - No destination: Just map the surroundings if enabled
   - Entity ID → lookup in Knowledge Base.
     - If human → enable leg tracking.
   - Direct pose → validate and transform as needed.
4. Navigation node computes path and publishes `cmd_vel` to simulation/hardware.
5. Orchestrator monitors progress and reports completion or errors back to Decision Making.

### Error handling 4

The MovementAction can be cancelled by the movement Orchestrator (or Decision Making) at any time. In this case an ActionResponse is still returned providing feedback to Decision Making allowing it to properly handle the error.

**Example — "Go to destination with mapping & localization active" (map pre-generated):**

1. Orchestrator receives: `activate_mapping=true`, `activate_localization=true`, plus destination.
2. Localization is started (flag true).
3. SLAM node is started (flag true).
4. Orchestrator identifies destination type: Entity ID.
5. Orchestrator queries the Knowledge Base for Entity metadata: Pose and pose_reference_frame.
6. Orchestrator transforms the entity pose from pose_reference_frame to the map frame.
7. Navigation node plans and publishes `cmd_vel` until the robot reaches the destination; Orchestrator reports status.

## Runtime Scenario 5 — Safety Monitoring (flawless vs. local issue)

### Flawless scenario 5

1. Safety submodules register with the central Safety Node.
2. Submodules continuously publish periodic status updates (heartbeats/health).
3. Central Safety Node aggregates statuses, detects no anomalies. When all is in order, no intervention is necessary.
4. Normal operation continues.

### Local fatal issue scenario 5

1. Safety submodules register with the central Safety Node.
2. Submodules continuously publish periodic status updates.
3. A submodule detects a fatal issue and reports it to the central Safety Node.
4. The Central Safety Node evaluates severity, context, and required handling.
5. The Central Safety Node sends out a RobotStatusEvent and initiates a system-wide freeze.
6. Decision Maker receives the RobotStatusEvent and cancels all running actions. It now waits for the next safety status event.
7. The Central Safety Node makes the Robot transition to a safe state. (e.g. blocking motor movement)
8. The Central Safety Node starts mitigation strategies (e.g. restarting nodes)
9. The Central Safety Node waits until a safe state has been reached (e.g. human left the vicinity, nodes have been restarted)
10. Central Safety Node sends out a RobotStatusEvent containing normal safety status
11. The Decision Maker resumes normal operation

### Local nonfatal issue scenario 5

1. Safety submodules register with the central Safety Node.
2. Submodules continuously publish periodic status updates.
3. A submodule detects a nonfatal issue and does not report it to the central Safety Node. It is only handled locally.
4. E.G. Speed to high
5. The local speed safety node forces the speed to 0.0 and triggers new planning on the movement orchestrator.

## Runtime Scenario 6 - Perception of a pickable object

1. Pickable object is in front of the robot camera
2. Object detection model detects the object and creates a bounding box or segmentation image
3. The depth pointcloud from the camera gets filtered by the boundingbox/segmentation
4. The object detection node builds a pickable Entity based on the object's center pose, detected class and pointcloud
5. The object detection node calls the database service to add it to the database
6. Currently unknown: At some point existing entities and newly detected ones have to be merged/deduplicated to enable tracking and avoid duplicates
   This step can either be done on the object detection side or as part of the database node.

## Runtime Scenario 7 - HRI + Vizbox: Robot requests the operator to open the cabinet door

1. Robot navigates to cabinet
2. Perception detects a closed cabinet door -> in database
3. Decision maker checks the is_open state of the cabinet -> it is closed
4. Decision maker sends a help request to the HRI with the message "Please open the cabinet door"
5. The HRI tells the LLM to rephrase the help request for the user
6. The LLM output is
   - converted into audio and output via the speakers
   - sent to the vizbox
   - is then part of the llm chat history
7. The Decision maker waits until the cabinet is detected open (checks the database every tick)
8. The Decision maker sends a feedback message to the HRI "Thank you" -> LLM -> Audio

If the waiting in 7. times out, the Decision maker retries from 4.

## Runtime Scenario 8 - HRI + Vizbox: The operator requests something from the robot

Note that this scenario is currently not a necessity since the tasks we aim for do not require it.

1. Operator talks to the robot
2. The VoiceActivityDetection node detects voice activity
3. The SpeechToText node starts converting audio into text
4. The text is fed into the llm with the request to check if it is relevant to the previous conversation or to the robot in general
5. If no the VoiceActivityDetection waits until it stops detecting voice for a certain amount of time and the cycle restarts from 1.
6. If yes the text is input
   - to the llm as a new user input
   - to the vizbox
   - is then part of the llm chat history
7. The LLM output is
   - converted into audio and output via the speakers
   - sent to the vizbox
   - is then part of the llm chat history
8. If the LLM also requests a tool call, the tool call is validated and sent to the Decision maker

The whole chat history is kept inside the LLM chat node and the oldest messages are discarded if the context gets too long
