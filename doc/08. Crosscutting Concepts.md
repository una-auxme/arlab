## Safety Node Structure

### Splitting safety responsibilities between local decentralized safety nodes and a central monitoring node

The system separates safety checks into two layers: local safety nodes attached to individual subsystems (e.g., manipulator, navigation, perception)
and a central monitoring node that aggregates their status. This design improves scalability by allowing each subsystem to handle immediate hazards locally while still enabling a unified,
system-wide assessment of critical issues. It also simplifies integration of new modules, as each only needs to provide its own local safety node.

### Cyclic publish–subscribe for module monitoring

To detect failures quickly, all safety nodes periodically publish heartbeat or status messages. The central safety node maintains a list of all active modules based on these cyclic updates.
Missing or erroneous updates can be immediately flagged, enabling fast error identification and centralized monitoring of system health.

## ROS 2 Package Structure

### Package Splitting  

The project is organized into distinct ROS 2 packages, each corresponding to a major functionality or architectural concern (e.g., manipulation, navigation, safety).
This modularization simplifies dependency management and allows packages to be developed, tested, and reused independently.

### Dependency management

Each ROS 2 package lists its dependencies in package.xml. Only non-python ROS dependencies are defined here, ensuring clean builds and proper dependency resolution when compiling the workspace.
Non-ROS dependencies (e.g. python) are handled separately.

#### Python Dependencies

For Python code, external dependencies are tracked in package specific requirements.txt files. All requirements files found in the repository are installed automatically when the docker is built.

Specific variants for GPU backends (CUDA, ROCm) or CPU-only installations are handled through separate requirement files:

- requirements.rocm.txt: For the ROCm flavor
- requirements.cuda.txt: For the CUDA flavor
- requirements.cpu.txt: For all other flavors

This is especially important for PyTorch.

### Build System

ROS 2 supports multiple build types. ament_python is used for Python-based packages, while ament_cmake is applied to C++ packages. Python code in ament_cmake packages is avoided.
Message definitions are placed into dedicated *_interfaces packages using ament_cmake, ensuring clean separation of interface definitions from implementation logic.

### Service Calling Conventions

Calling blocking functions (services) inside a callback (timer, subscription, etc..) can lead to deadlocks with the default single-threaded executor. [Source](https://docs.ros.org/en/jazzy/How-To-Guides/Sync-Vs-Async.html)
Template nodes use asynchronous callbacks and asynchronous service calls combined with a separate MutuallyExclusiveCallbackGroup to prevent deadlocks. This Callbackgroup has to be used for all callbacks that use services.
This is mandatory to avoid locking up the rclpy executer.

The async approach was chosen instead of a multithreaded executer because it uses less resources.

## Controlling Subsystems with Actions

### ManipulationAction / MovementAction common attributes

Actions are used to control long-running tasks such as robot manipulation or navigation. The architecture defines shared attributes and semantics for different action types,
ensuring consistency in how goals, feedback, and results are structured.

### Action usage and general ROS behavior

ROS actions extend the service concept by supporting feedback and cancellation. Subsystems such as movement and manipulation expose their capabilities via actions,
enabling high-level orchestration to send commands, monitor progress, and interrupt tasks when needed.
This provides robust and flexible control over robot behaviors.

## Future Possible Concepts

This chapter contains possible concepts that we should use in the following semesters.

### Async Timeouts for Service Calls

Introducing explicit timeouts for asynchronous service calls would allow nodes to recover gracefully if a service is unavailable or too slow.
This prevents indefinite blocking and makes error handling more robust, especially in distributed systems with varying network delays.
A possible approach can be found here: <https://superfastpython.com/asyncio-timeout/>.
This requires the usage of the [asyncio executor](../code/arlab_asyncio_executor).

### Topic / Service Communication Patterns

#### Best practices for topic naming

Following consistent naming conventions (e.g., /topic_name vs. /topic_name/data) improves readability, avoids collisions, and clarifies whether a topic contains raw data, processed results, or control signals.
Naming conventions have not been established yet, but they should be in place when integrating all nodes with each other.

Considerations:

- Absolute topic paths vs relative topic paths with namespaces (in launch file)

#### QoS policy configuration

Quality of Service (QoS) settings control reliability, durability, and history of messages. Careful configuration ensures that critical messages (e.g., safety alerts) are always delivered reliably,
while high-frequency sensor data can use best-effort delivery to reduce network load. QoS conventions have not been established yet. Many of them have to be set based on system performance.

### Parameter

Using parameters allows for configuration changes without redeployment. This increases testing capabilities.

Parameters can be dynamically queried and updated at runtime using the rcl_get_parameter() and rcl_set_parameter() APIs.
Supported parameter types include primitives (int, float, bool), arrays, and dictionaries, giving developers flexibility in expressing configuration values.
Parameters can be overridden from launch files, enabling different runtime configurations for development, testing, and production without modifying source code.

Parameter updates can be further simplified by updating them based on python attribute names.
