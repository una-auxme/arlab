*Overview:*
This chapter summarizes the solution strategies for the project. For each subsection the key architectural decisions and the corresponding motivations and main trade-offs are explained.
Each decision is motivated by the underlying problem statement, the project’s quality goals, and the key constraints explained previously. Details and implementation specifics are provided in the following subsections.

## 4.1 Decision-Making and Task Orchestration

*Approach:* Behavior trees govern high-level decision-making and sequencing of tasks. A single orchestrator exposes a unified interface for high-level decisions and delegates low-level motion or drive commands to the manipulator or movement nodes (e.g., MoveIt2, Nav2).

*Motivations:*

- Behavior trees are simple, readable, and effective for fixed task sets. They integrate well with ROS actions and make the system easier to test and extend.
- The orchestrators publish/subscribe style for motion or drive commands enforce loose coupling between task logic and motion planning. Therefore, improving modularity and testability.

## 4.2 Knowledge Base and Data Flow

*Approach:* A relational database as the central knowledge base is being used and the database schema is implemented by using SQL-Alchemy and defined via python classes.
Conversion functions between Python classes and ROS messages for ROS service are provided. To improve throughput, an Async service callback that uses a custom ROS executor has been integrated with asyncio.

*Motivations:*

- A relational database is reliable and sufficient where little semantic complexity is required.
- Python library provided by SQL-Alchemy (Async API) is proven, popular and easy to use and has an ORM with support for Python classes.
- Async service callbacks allow multiple simultaneous service requests without the need for additional threads and therefore improving throughput and responsiveness for multiple concurrent clients.

## 4.3 Human–Robot Interaction (HRI)

*Approach (currently only planned):* Use of AI-based libraries and large language model (LLM) tooling for flexible, natural interaction.
Classic Wake-Word detection are replaced with voice-activity detection (VAD) combined with LLM-based relevance checks. For natural speech output ai based text-to-speech (TTS) is being used.

*Motivations & Trade-Offs:*

- LLMs with tool support enable fluid, extensible dialogues compared to static state machines. Therefore, LLMs are good for natural interaction and future feature growth.
-> But they are harder to fully control and may produce unexpected outputs.
- VAD together with relevance checks reduce missed activations caused by unreliable open source Wake-Word detectors.
-> But they produce slightly higher false-positive risks

## 4.4 Manipulation and Motion Planning

*Approach:* For path and motion planning the open-source software MoveIt2 is used. A orchestrator sends driving and pose commands to MoveIt2 through a message-based interface.
Grip force is determined dynamically based on object classification results from the perception pipeline. The movement and strategies of the manipulation can be validated in the simulation (Gazebo) before sending the commands to the real hardware.

*Motivations & Trade-Offs:*

- MoveIt2 is an established framework that reduces custom implementation effort and provides robust, collision-aware motion planning, inverse kinematics and trajectory generation.
-> But because of better documentation a few features had to be integrated with C++ and not Python
- The use of an orchestrator enables loose coupling between high-level task logic and low-level motion planning, better testing
- Deciding gripping force locally in the manipulator module keeps the relevant logic where it belongs and reduces cross-module complexity.
- Simulation-first development mitigates risk while physical hardware is not yet ready.

## 4.5 Navigation and Movement Stack

*Approach:* The Movement Orchestrator handles high-level movement directives and forwards them to established navigation components (Nav2) and SLAM modules.
Where appropriate, the commands are split between global (high-level) and local (low-level) controllers. Simulation-based testing is used until the hardware is available.

*Motivations:*

- Nav2 together with SLAM is a proven combination and reduces overall engineering risk.
-The orchestrator’s single interface simplifies global decision logic while delegating execution to specialized motion stacks.

## 4.6 Computer Vision & Perception

*Approach:* Use of a YOLO-family deep learning object detector on Jetson-class hardware for real-time, multi-class detection. Models are augmented and fine-tuned with grocery-specific datasets (e.g., public Kaggle datasets) for task-specific accuracy.
An Output of the Computer Vision to the central knowledge base is provided so all modules can access the data of detected object.
Temporarily an Azure Kinect DK is being. The Intel RealSense (SR305) had issues because of defect hardware and hardware drivers being incompatible with python versions and libraries.

*Motivations & Trade-offs:*

- YOLO delivers high accuracy across many object classes, handles complex scenes and small objects and runs real-time on modern edge hardware (Jetson).  
-> But YOLO often requires powerful hardware, has significant power consumption and demands substantial resources for training.
- Offloading detected object metadata to the knowledge base preserves clean separation of concerns and makes perception outputs widely accessible.

## 4.7 Safety Architecture

*Approach:* A hybrid safety architecture has been designed consisting of decentralized safety submodules and a central safety node that aggregates status and enforces system-wide reactions. Simple safety submodule templates are provided for teams to implement local checks and reports.

*Motivations:*

- Scalability & efficiency: Provided templates let each sub-team implement safety locally without requiring a dedicated safety team, speeding development.
- Simplicity & adaptability: Local safety sub-modules keep safety checks close to local functionality and parameters. This allows for quick adjustments and simplifies updates as features evolve.
- Error transparency & consistency: The central safety node collects all submodule states, evaluates severity, and ensures uniform reactions across the system.
- Reliability & compliance: Centralized reporting ensures robustness, provides reliable monitoring, and creates a single point of truth for audits and certification. Therefore, making sure that failures in local safety modules can not compromise the overall safety.

## 4.8 Validation & Known Limitations

*Validations:*

- Simulation-first validation used for testing manipulation and navigation functions (Gazebo + MoveIt2).
- Computer Vision will use on-hardware tests once drivers and camera hardware are stabilized (current temporary camera: Azure Kinect DK; long-term target: Intel RealSense).
-> Initial YOLO 11 Nano experiments on Jetson hardware produced promising grocery-detection results. Additional domain-specific training is planned.

*Known limitations and mitigation:*

- Hardware driver incompatibility (Intel RealSense vs. current Python environment) requires a temporary camera substitution. Ongoing work targets driver fixes or upstream upgrades.
- LLM-driven HRI introduces unpredictability. Mitigate this by defining clear task tools and guardrails, using relevance checks and logging for traceability.
