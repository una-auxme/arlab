*Overview:*
This chapter summarizes the solution strategies for the project. For each subsection the key architectural decisions and the corresponding motivations and main trade-offs are explained. Each decision is motivated by the underlying problem statement, the project’s quality goals, and the key constraints explained previously. Details and implementation specifics are provided in the following subsections.

## 4.1 Decision-Making and Task Orchestration

*Approach:* Behavior trees govern high-level decision-making and sequencing of tasks. A single orchestrator exposes a unified interface for high-level decisions and delegates low-level motion or drive commands to the manipulator or movement nodes (e.g., MoveIt2, Nav2).

*Motivations:*

- Behavior trees are simple, readable, and effective for fixed task sets. They integrate well with ROS actions and make the system easier to test and extend.
- The orchestrators publish/subscribe style for motion or drive commands enforce loose coupling between task logic and motion planning. Therefore, improving modularity and testability.

## 4.2 Knowledge Base and Data Flow

*Approach:* A relational database as the central knowledge base is being used and the database schema is implemented by using SQL-Alchemy and defined via python classes. Conversion functions between Python classes and ROS messages for ROS service are provided. To improve throughput, an Async service callback that uses a custom ROS executor has been integrated with asyncio.

*Motivations:*

- A relational database is reliable and sufficient where little semantic complexity is required.
- Python library provided by SQL-Alchemy (Async API) is proven, popular and easy to use and has an ORM with support for Python classes.
- Async service callbacks allow multiple simultaneous service requests without the need for additional threads and therefore improving throughput and responsiveness for multiple concurrent clients.

## 4.3 Human–Robot Interaction (HRI)

*Approach (currently only planned):* Use of AI-based libraries and large language model (LLM) tooling for flexible, natural interaction. Classic Wake-Word detection are replaced with voice-activity detection (VAD) combined with LLM-based relevance checks. For natural speech output ai based text-to-speech (TTS) is being used.

*Motivations & Trade-Offs:*

- LLMs with tool support enable fluid, extensible dialogues compared to static state machines. Therefore, LLMs are good for natural interaction and future feature growth.
-> But they are harder to fully control and may produce unexpected outputs.
- VAD together with relevance checks reduce missed activations caused by unreliable open source Wake-Word detectors.
-> But they produce slightly higher false-positive risks

## 4.4 Manipulation and Motion Planning

*Approach:* For path and motion planning the open-source software MoveIt2 is used. A orchestrator sends driving and pose commands to MoveIt2 through a message-based interface. Grip force is determined dynamically based on object classification results from the perception pipeline. The movement and strategies of the manipulation can be validated in the simulation (Gazebo) before sending the commands to the real hardware.

*Motivations & Trade-Offs:*

- MoveIt2 is an established framework that reduces custom implementation effort and provides robust, collision-aware motion planning, inverse kinematics and trajectory generation.
-> But because of better documentation a few features had to be integrated with C++ and not Python
- The use of an orchestrator enables loose coupling between high-level task logic and low-level motion planning, better testing
- Deciding gripping force locally in the manipulator module keeps the relevant logic where it belongs and reduces cross-module complexity.
- Simulation-first development mitigates risk while physical hardware is not yet ready.
